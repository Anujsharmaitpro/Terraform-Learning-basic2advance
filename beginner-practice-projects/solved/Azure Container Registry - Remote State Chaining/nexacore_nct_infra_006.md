## 1. Project Overview

### What You Are Building

**Two independent Terraform configurations that share data through
remote state — one provisions an Azure Container Registry, the other
provisions an App Service that reads the registry details from the
first config's state.**

```

│  CONFIG A: nct-infra-006-registry/                              │
│                                                                 │
│  Azure Container Registry (nct-dev-registry)                    │

```

### The Two New Concepts

**New Concept 1 — Azure Container Registry (ACR)**

ACR is Azure's private Docker image registry. Instead of pushing
Docker images to public Docker Hub, your team pushes to a URL like:
```
nctdevregistry.azurecr.io/myapp:latest
```

Only identities with the right permissions can pull from it.
In this project you provision the registry itself. You do not push
any actual Docker images — that is the dev team's job. Your job is
the infrastructure.

**New Concept 2 — `terraform_remote_state` Data Source**

You already know data sources read from Azure. This data source
reads from another Terraform state file. It lets Config B say:
*"Give me the outputs that Config A produced after its last apply."*

```hcl
# Config B reads Config A's outputs like this:
data "terraform_remote_state" "registry" {
  backend = "azurerm"
  config = {
    resource_group_name  = "nct-tfstate-rg"
    storage_account_name = "ncttfstate20240101"
    container_name       = "tfstate"
    key                  = "nct-infra-006/registry/terraform.tfstate"
  }
}

# Then use the values like this:
data.terraform_remote_state.registry.outputs.registry_login_server
```

No hardcoding. No copy-pasting. When the registry changes,
Config B automatically gets the updated values on next apply.

## 2. Naming Conventions

### ACR Naming — Strict Rules

Container Registry names are **globally unique**, **5–50 characters**,
**alphanumeric only** — no hyphens, no underscores. Similar restriction
to Storage Accounts.

```
Pattern:  {orgprefix}{env}registry{initials}
Example:  nctdevregistryjd
```

## 3. Core Components to Build

### Component 1 — Config A: Azure Container Registry

**Folder:** `registry/`

This is the self-contained first config. It provisions the registry
and exposes its details as outputs. Config B will read those outputs.

**Resources to define in `registry/main.tf`:**

`azurerm_resource_group` — you know this pattern

`azurerm_container_registry`:
- `name` — from variable, alphanumeric only
- `resource_group_name` — from RG attribute
- `location` — from RG attribute
- `sku` = `"Basic"` — cheapest tier, sufficient for dev
- `admin_enabled` = `true`
  This enables a simple username/password for registry access.
  In production you would use managed identity instead.
  For this project, admin credentials are intentional —
  they are what App Service uses to pull images.
- All six org tags

**Outputs to define in `registry/outputs.tf`:**

```
registry_login_server     ← azurerm_container_registry.acr.login_server
registry_name             ← azurerm_container_registry.acr.name
registry_admin_username   ← azurerm_container_registry.acr.admin_username
registry_admin_password   ← azurerm_container_registry.acr.admin_password
resource_group_name       ← azurerm_resource_group.registry_rg.name
```

> `registry_admin_password` is sensitive. Mark it with `sensitive = true`
> in outputs.tf. You know how to do this from NCT-INFRA-004.

### Component 3 — Config B: Remote State Data Source

**File:** `appservice/data.tf`

This is the new concept. This data source reads Config A's outputs
from the remote state file Config A wrote to Azure Blob Storage.

**You must define `data "terraform_remote_state" "registry"`:**

```hcl
data "terraform_remote_state" "registry" {
  backend = "azurerm"

  config = {
    resource_group_name  = "nct-tfstate-rg"
    storage_account_name = "ncttfstate20240101"   # your bootstrap SA name
    container_name       = "tfstate"
    key                  = "nct-infra-006/registry/terraform.tfstate"
  }
}
```

After this is declared, you access Config A's outputs like this:
```hcl
data.terraform_remote_state.registry.outputs.registry_login_server
data.terraform_remote_state.registry.outputs.registry_admin_username
data.terraform_remote_state.registry.outputs.registry_admin_password
```

**Critical rule:** Config A must be applied before Config B can be
planned or applied. If the state file does not exist yet,
`terraform_remote_state` will fail with a storage error.

### Component 4 — Config B: App Service Plan + App Service

**File:** `appservice/main.tf`

You have built both of these in NCT-INFRA-005. The structure is
identical. What is different is the `app_settings` block — this
time the registry values come from the remote state data source,
not from Key Vault.

**`azurerm_resource_group`** — you know this

**`azurerm_service_plan`:**
- `os_type` = `"Linux"`
- `sku_name` = `"F1"`
- All six org tags

**`azurerm_linux_web_app`:**

`site_config` block:
```hcl
site_config {
  always_on = false
  application_stack {
    docker_image_name        = "nginx:latest"
    docker_registry_url      = "https://${data.terraform_remote_state.registry.outputs.registry_login_server}"
    docker_registry_username = data.terraform_remote_state.registry.outputs.registry_admin_username
    docker_registry_password = data.terraform_remote_state.registry.outputs.registry_admin_password
  }
}
```

> Using `nginx:latest` as a placeholder image — it is a public image
> that will work even before any NexaCore images are pushed to the
> registry. In production this would be `nctdevregistryjd.azurecr.io/nctapp:latest`.

`app_settings` block:
```hcl
app_settings = {
  "DOCKER_REGISTRY_SERVER_URL"      = "https://${data.terraform_remote_state.registry.outputs.registry_login_server}"
  "DOCKER_REGISTRY_SERVER_USERNAME" = data.terraform_remote_state.registry.outputs.registry_admin_username
  "DOCKER_REGISTRY_SERVER_PASSWORD" = data.terraform_remote_state.registry.outputs.registry_admin_password
  "WEBSITES_PORT"                   = "8000"
  "WEBSITE_RUN_FROM_PACKAGE"        = "1"
}
```

`lifecycle` block — same pattern as NCT-INFRA-005:
```hcl
lifecycle {
  ignore_changes = [
    app_settings["WEBSITE_RUN_FROM_PACKAGE"]
  ]
}
```

## 4. Hints & Pitfalls

### Hint 1 — Apply Order Is Enforced by Logic, Not by Terraform

Terraform does not know that Config B depends on Config A.
They are completely separate workspaces. If you try to
`terraform plan` in `appservice/` before Config A has been applied,
you will get an error like:

```
Error: Unable to read remote state
  Failed to retrieve state: blob not found
```

The state file Config B is trying to read simply does not exist yet.

**The enforced order is always:**
```
1. cd registry/    → terraform apply   (creates the state file)
2. cd appservice/  → terraform apply   (reads that state file)
```

Write this in your notes. It is a team process rule, not just a
technical one — in real orgs, the registry team applies their config
first, then notifies the app team to apply theirs.

---

### Hint 2 — ACR Admin Password Is Marked Sensitive — Outputs Need Special Handling

The `admin_password` from `azurerm_container_registry` is automatically
marked as sensitive by the Azure provider. When you reference it in
Config B's `app_settings`, Terraform will mark the entire `app_settings`
map as sensitive in plan output.

This means `terraform plan` will show:
```
+ app_settings = (sensitive value)
```

Instead of showing each individual setting. This is expected behaviour —
not a bug. The password being in the map causes the whole map to be
redacted. You can still verify the settings were applied after `apply`
using the Azure CLI:

```powershell
az webapp config appsettings list `
  --name nct-dev-006-web-jd `
  --resource-group nct-dev-006-app-rg `
  --output table
```

---

### Hint 3 — ACR `Basic` SKU and Free App Service Have a Compatibility Note

The `F1` (Free) App Service tier does not support pulling from private
registries in all configurations. If you see the App Service created
successfully but the container fails to start, this is why.

For this project the goal is provisioning the infrastructure correctly —
not actually running a container. The `terraform apply` completing
successfully and the App Service existing with the correct `app_settings`
is the definition of done here.

Verify success with outputs and the Azure CLI check in Hint 2 —
not by expecting the app URL to serve content.

```powershell
# ── Phase 1: Config A — Registry ─────────────────────────────────

cd C:\Projects\nct-infra-006\registry

terraform init

# registry_login_server   = "nctdevregistryjd.azurecr.io"

# registry_admin_username = "nctdevregistryjd"

# ── Phase 2: Config B — App Service ──────────────────────────────

cd ..\appservice

terraform init

terraform fmt
terraform plan

terraform apply
# Type: yes

# Verify app settings reference the correct registry

  --name nct-dev-006-web-jd `
  --resource-group nct-dev-006-app-rg `
  --output table

# Verify remote state output
terraform output registry_connected_to
# Should print: nctdevregistryjd.azurecr.io


# ── Destroy — in reverse order ────────────────────────────────────

# Destroy appservice first
cd ..\appservice
terraform destroy
# Type: yes

# Then destroy registry
cd ..\registry
terraform destroy
# Type: yes

# Verify both RGs are gone
az group list --output table
# nct-dev-registry-rg and nct-dev-006-app-rg should not appear
```

## 6. Verification — Prove the Remote State Chain Works

This is the most important verification step in this project.
Do not skip it.

```powershell
# After both configs are applied:

# Step 1: Check Config A state file exists in Azure Blob
az storage blob list `
  --account-name ncttfstate20240101 `
  --container-name tfstate `
  --output table
# Expected entries:
# nct-infra-006/registry/terraform.tfstate     ← Config A wrote this
# nct-infra-006/appservice/terraform.tfstate   ← Config B wrote this

# Step 2: Confirm App Service is using the registry login server from Config A
$registryServer = (terraform output -raw registry_connected_to)
Write-Host "App Service connected to registry: $registryServer"

# Step 3: Compare with what Config A output directly
cd ..\registry
$acrServer = (terraform output -raw registry_login_server)
Write-Host "ACR login server from Config A: $acrServer"

# Both values should be identical
# This proves the chain: Config A output → remote state → Config B setting
```
