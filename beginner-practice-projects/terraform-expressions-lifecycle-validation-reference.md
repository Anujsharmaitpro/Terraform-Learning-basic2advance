You asked for separate files covering expressions, dynamic expressions,
conditional and splat expressions, lifecycle rules, dynamic blocks, and
validation. These features are tightly related — dynamic blocks

## 1. What Is an Expression, Precisely?

An **expression** is any piece of Terraform configuration that
produces a value, rather than declaring a block. A literal string, a
reference to a variable, a function call, a conditional, a `for`
loop — all of these are expressions. Terraform's HCL (HashiCorp
Configuration Language) allows expressions almost anywhere a value is
expected: as a resource argument, inside a `locals` block, as an
output's `value`, or inside a `validation` condition.

```hcl
"West Europe"                      # a literal expression
var.location                       # a reference expression
upper(var.environment)             # a function-call expression
var.environment == "prod" ? 1 : 0  # a conditional expression
[for x in var.list : upper(x)]     # a for expression
```

Everything covered in this guide is a specific *kind* of expression, or
a language feature (dynamic blocks, lifecycle, validation) that's
built around evaluating expressions at a particular point in a
resource's configuration or lifecycle.

## 2. Reference Expressions — The Building Block

Before the more advanced expression types, it's worth being precise
about the four reference forms everything else builds on:

```hcl
var.environment                          # an input variable
local.common_tags                        # a local value
azurerm_resource_group.rg.location        # a managed resource's attribute
data.azurerm_client_config.current.tenant_id  # a data source's attribute
module.networking.subnet_id              # a child module's output
```

Each of these resolves to a concrete value once Terraform has enough
information to compute it (immediately for variables/locals with
literal defaults, only after `apply` for many resource attributes
generated by the cloud provider, such as an auto-assigned ID).

## 3. String Interpolation and Templates

Embedding an expression inside a string uses `${ }`:

```hcl
name = "${var.project}-${var.environment}-rg"
# project="myapp", environment="dev" -> "myapp-dev-rg"
```

**A precision worth noting:** if the entire value of an argument is a
single interpolation with nothing else around it, HCL lets you drop
the interpolation syntax entirely — `name = var.project` and
`name = "${var.project}"` are equivalent, and the plain form is
preferred style. The `${ }` form is only necessary when you're
embedding an expression *inside* a larger literal string, as in the
example above.

**Heredoc templates** (multi-line strings, commonly used for scripts
passed to `custom_data`) use the same interpolation syntax internally:

```hcl
custom_data = base64encode(<<-EOF
  #!/bin/bash
  echo "Deploying to ${var.environment}"
  apt-get update
EOF
)
```

## 4. Conditional Expressions

### Syntax

```hcl
condition ? true_value : false_value
```

This is a ternary operator, borrowed from the same syntax used in C,
Java, JavaScript, and many other languages. Terraform evaluates
`condition` (which must resolve to a `bool`), and returns
`true_value` if it's `true`, `false_value` otherwise.

### Example

```hcl
resource "azurerm_storage_account" "example" {
  account_replication_type = var.environment == "prod" ? "GRS" : "LRS"
}
```

### Using it for conditional resource creation

Combined with `count`, this is the standard idiom for making a whole
resource optional:

```hcl
resource "azurerm_monitor_action_group" "example" {
  count = var.enable_alerting ? 1 : 0
  # ...
}
```

When `count` is `0`, Terraform creates zero instances of this resource
— effectively "off." Referencing it elsewhere then requires index or
splat syntax (Section 6), since `count`-based resources are always
addressed as a list, even when there's only one or zero instances.

### Nesting — a genuine readability warning, not just a style preference

```hcl
name = var.env == "prod" ? "prod-rg" : var.env == "dev" ? "dev-rg" : "stage-rg"
```

This works, but readability degrades sharply past one level of
nesting. Once you have more than two possible outcomes, a `lookup()`
against a map (Section 14 of the Terraform functions reference) is
almost always clearer:

```hcl
locals {
  rg_name = lookup(
    { prod = "prod-rg", dev = "dev-rg" },
    var.env,
    "stage-rg"
  )
}
```

### A type-consistency requirement worth knowing

Both branches of a conditional expression should generally resolve to
the *same type*. Terraform will attempt to reconcile mismatched types
(for example, a number in one branch and a string in the other) by
converting where it safely can, but relying on that implicit
conversion is fragile and worth avoiding deliberately — keep both
branches the same type.

## 5. `for` Expressions

A `for` expression transforms one collection into another — a
different, more general tool than a conditional expression, and the
one splat expressions (Section 6) are actually shorthand for.

### Producing a list

```hcl
[for s in var.subnet_names : upper(s)]
# ["WEB", "APP", "DB"] if var.subnet_names = ["web", "app", "db"]
```

### Producing a map

```hcl
{for s in var.subnet_names : s => upper(s)}
# {"web" = "WEB", "app" = "APP", "db" = "DB"}
```

### Filtering with `if`

```hcl
[for s in var.subnet_names : s if s != "db"]
# ["web", "app"] — "db" excluded
```

### Iterating over a map, accessing both key and value

```hcl
{for k, v in var.tags : k => upper(v)}
```

### Grouping (the `...` symbol has a special meaning here)

```hcl
{for s in var.subnet_names : substr(s, 0, 1) => s...}
# groups values sharing the same first-letter key into a list
```

This grouping form of `for` is genuinely obscure and rarely needed —
included here for completeness, not because you should reach for it
by default.

## 6. Splat Expressions

### What it is

Splat is shorthand for the single most common `for`-expression
pattern: "give me this one attribute from every item in a list."

```hcl
azurerm_storage_account.example[*].name
# shorthand for:
[for sa in azurerm_storage_account.example : sa.name]
```

### The hard limitation: lists only

Splat (`[*]`) only works on **lists** — including `count`-created
resource collections, which Terraform represents as a list indexed by
integer. It does **not** work on sets, maps, or `for_each`-created
resource collections (which Terraform represents as a *map*, keyed by
the `for_each` key, not a list).

```hcl
# count-based resource — splat works directly
resource "azurerm_storage_account" "example" {
  count = 3
  # ...
}
output "names" {
  value = azurerm_storage_account.example[*].name   # works
}

# for_each-based resource — splat does NOT work directly
resource "azurerm_storage_account" "example2" {
  for_each = toset(["a", "b", "c"])
  # ...
}
output "names2" {
  value = azurerm_storage_account.example2[*].name   # does NOT work — this is a map, not a list
}
```

For a `for_each`-created resource, use `values()` to convert the map
to a list first, then splat that:

```hcl
output "names2" {
  value = values(azurerm_storage_account.example2)[*].name
}
```

or, equally valid and arguably clearer, skip splat entirely and use a
`for` expression directly, which works uniformly on both maps and lists:

```hcl
output "names2" {
  value = [for sa in azurerm_storage_account.example2 : sa.name]
}
```

### Legacy splat syntax — recognize it, don't write it

You may encounter an older syntax, `resource.name.*.attribute`
(a dot before the asterisk, positioned differently), in codebases
predating Terraform 0.12. This "legacy splat" has more restrictive
behavior than the modern `[*]` form. Terraform still parses it for
backward compatibility, but there's no reason to write it in new
code — always use `[*]`.

### Combining splat with an index

```hcl
azurerm_storage_account.example[*].name[0]
# equivalent to: azurerm_storage_account.example[0].name
```

Both forms are valid; the second is more direct when you specifically
want a single element rather than "all elements, then pick one."

## 7. Dynamic Blocks

### What they solve

Dynamic blocks let you generate a variable number of **repeatable
nested configuration blocks** inside a resource, based on a
collection, instead of writing each one out literally.

### The critical distinction dynamic blocks don't solve

**A dynamic block generates nested blocks — not top-level arguments.**
This is a genuinely common point of confusion worth stating precisely:
if you want to conditionally set a plain argument's value (not a whole
repeatable nested block), that's a job for a conditional expression
(Section 4) directly on the argument, not a `dynamic` block. `dynamic`
only ever produces zero or more instances of a *nested block* — things
like `security_rule { }` inside an NSG, or `ip_configuration { }`
inside a network interface, which can legitimately appear multiple
times inside their parent resource.

### Full syntax, every part named

```hcl
dynamic "security_rule" {
  for_each = local.nsg_rules
  iterator = "rule"                 # optional — renames the loop variable
  content {
    name     = rule.key
    priority = rule.value.priority
    # ... other fields referencing rule.value.* ...
  }
}
```

- `dynamic "security_rule"` — the label matches the actual nested
  block type name from the resource's own schema (`security_rule`
  here, because that's the real Azure NSG rule block name)
- `for_each` — the collection to iterate; a map or set, following
  exactly the same map/set requirement as a resource-level `for_each`
- `iterator` — **optional**, and genuinely useful once you have nested
  `dynamic` blocks inside each other, where the default iterator name
  (matching the label) would otherwise collide between the outer and
  inner block. Without `iterator`, the loop variable's default name is
  identical to the `dynamic` block's own label — so `dynamic
  "security_rule"` gives you a variable named `security_rule` inside
  `content`, exactly as shown in earlier examples in this series.
- `content { }` — mandatory; the template for one instance of the
  generated block

### Example: nested dynamic blocks needing `iterator`

```hcl
dynamic "ip_configuration" {
  for_each = var.ip_configs
  iterator = "ipconf"
  content {
    name      = ipconf.key
    subnet_id = ipconf.value.subnet_id

    dynamic "public_ip_address" {
      for_each = ipconf.value.public_ip_id != null ? [ipconf.value.public_ip_id] : []
      content {
        id = public_ip_address.value
      }
    }
  }
}
```

Note the inner dynamic block's `for_each` uses a conditional
expression producing either a one-element list or an empty list — a
common idiom for making a nested block *optional* based on a condition,
since `for_each` over an empty collection simply produces zero
instances of the block.

### When not to use dynamic blocks

Direct guidance worth restating plainly: if a resource has a fixed,
small, unchanging number of a given nested block (say, always exactly
one `os_disk { }`), writing it directly is clearer than wrapping it in
`dynamic` for no real benefit. Reach for `dynamic` specifically when
the *number* of nested blocks genuinely varies based on input data —
not as a default habit for every nested block you write.

## 8. Lifecycle Meta-Argument Block

The `lifecycle` block, nested inside a `resource` block, controls how
Terraform manages that resource's create/update/destroy behavior —
distinct from the resource's own configuration arguments.

### `create_before_destroy`

```hcl
resource "azurerm_storage_account" "example" {
  # ...
  lifecycle {
    create_before_destroy = true
  }
}
```

Forces Terraform to create the replacement resource *before*
destroying the old one, when a change forces replacement — minimizing
downtime, at the cost of briefly having two instances of a resource
that may need a globally unique name to coexist (which can itself
cause the create step to fail if the new name isn't actually
different — worth checking before relying on this for a
uniquely-named resource type).

**A propagation subtlety worth knowing:** if resource B depends on
resource A, and A is marked `create_before_destroy`, Terraform may
require B to also be marked `create_before_destroy` in certain
replacement scenarios, or the plan can fail with a dependency-ordering
error. This isn't universal to every dependency chain, but it's worth
checking for if you add `create_before_destroy` to a resource with
downstream dependents and hit an unexpected planning error.

### `prevent_destroy`

```hcl
lifecycle {
  prevent_destroy = true
}
```

Blocks *any* operation that would destroy this resource, including
`terraform destroy` and a replacement triggered by a forces-replacement
change — until this line is removed or set to `false`. There is no
"break glass" flag to override it at apply time by design; you must
edit the configuration itself, which is the deliberate friction point.

### `ignore_changes`

```hcl
lifecycle {
  ignore_changes = [tags]
}
# or, for every attribute (not combinable with a specific list):
lifecycle {
  ignore_changes = all
}
```

Tells Terraform to stop treating differences in the listed
attribute(s) as changes to apply — useful when something outside
Terraform (an autoscaler, a platform policy engine like Azure Policy's
tag-appending behavior) legitimately modifies that attribute and you
don't want every `plan` fighting it. `ignore_changes = all` and a
specific attribute list are mutually exclusive — you pick one form or
the other, not both together.

### `replace_triggered_by`

```hcl
lifecycle {
  replace_triggered_by = [
    azurerm_resource_group.rg.id
  ]
}
```

Forces this resource to be destroyed and recreated whenever the
referenced resource or attribute changes — even if nothing in *this*
resource's own configuration changed. Useful for forcing a rebuild
tied to an external trigger (a script's content hash, a related
resource's ID). Worth knowing this can only reference other managed
resources or their attributes, not data sources, and cannot reference
the resource's own attributes (referencing itself doesn't make sense
for this particular meta-argument).

## 9. Variable Validation Blocks

### Syntax

```hcl
variable "environment" {
  type = string

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Environment must be dev, staging, or prod."
  }
}
```

`condition` must be a boolean expression; if it evaluates to `false`,
Terraform halts with `error_message` shown to the user, before any
plan or apply proceeds further.

### Multiple validation blocks on one variable

```hcl
variable "vm_size" {
  type = string

  validation {
    condition     = length(var.vm_size) >= 2 && length(var.vm_size) <= 30
    error_message = "vm_size must be between 2 and 30 characters."
  }

  validation {
    condition     = strcontains(lower(var.vm_size), "standard")
    error_message = "vm_size must contain the keyword 'standard'."
  }
}
```

Every `validation` block on a variable is checked independently — all
must pass.

### A precise, version-dependent rule worth knowing

**Referencing other variables inside a `validation` condition** was
not permitted in Terraform versions before 1.9 — a validation
condition could only reference the variable it was attached to (plus
functions and literal values), not a *different* variable declared
elsewhere in the same configuration. Terraform 1.9 lifted this
restriction, allowing cross-variable validation like this:

```hcl
variable "min_count" {
  type = number
}

variable "max_count" {
  type = number

  validation {
    condition     = var.max_count >= var.min_count
    error_message = "max_count must be greater than or equal to min_count."
  }
}
```

If you're on an older Terraform version and this pattern produces an
error about referencing an undeclared variable or an unsupported
attribute, check `terraform version` before assuming your syntax is
wrong — this specific capability is genuinely version-gated, not a
universal HCL feature.

## 10. `precondition` and `postcondition` — Validation Inside Lifecycle

These live inside a `lifecycle` block (not attached to a `variable`),
and were introduced in Terraform 1.2 — worth checking your version if
these blocks produce an "unsupported block type" error.

### `precondition` — checked before the resource is created/updated

```hcl
resource "azurerm_resource_group" "rg" {
  name     = "rg-${var.environment}"
  location = var.location

  lifecycle {
    precondition {
      condition     = contains(var.allowed_locations, var.location)
      error_message = "Location must be one of the approved regions."
    }
  }
}
```

### `postcondition` — checked after the resource is created/updated, using `self`

```hcl
resource "azurerm_linux_virtual_machine" "vm" {
  # ...
  lifecycle {
    postcondition {
      condition     = self.public_ip_address != null
      error_message = "VM was created without a public IP address."
    }
  }
}
```

`self` refers to the resource's own resulting attributes after
creation — the only place in Terraform where you reference a
resource's attributes without its full type-and-name path, since
you're already inside that resource's own block.

### How this differs from `validation`

`validation` blocks live on a `variable` and check an *input* before
anything is created. `precondition`/`postcondition` live inside a
specific *resource's* `lifecycle` block and can check conditions
involving that resource's own configuration or (for `postcondition`)
its actual resulting state — checks that genuinely can't be expressed
at the variable level, because they depend on values only known once
Terraform has resolved a specific resource's configuration or created it.

## 11. How These Features Combine in Practice

A realistic pattern combining several of these together — a
dynamic block whose content depends on a conditional expression,
guarded by a variable validation, and the resource itself protected by
a lifecycle rule:

```hcl
variable "environment" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Environment must be dev, staging, or prod."
  }
}

locals {
  nsg_rules = {
    allow_http = {
      priority = 100
      port     = "80"
    }
    allow_https = {
      priority = 110
      port     = "443"
    }
  }
}

resource "azurerm_network_security_group" "nsg" {
  name                = var.environment == "prod" ? "prod-nsg" : "nonprod-nsg"
  resource_group_name = azurerm_resource_group.rg.name
  location            = azurerm_resource_group.rg.location

  dynamic "security_rule" {
    for_each = local.nsg_rules
    content {
      name                       = security_rule.key
      priority                   = security_rule.value.priority
      direction                  = "Inbound"
      access                     = "Allow"
      protocol                   = "Tcp"
      source_port_range          = "*"
      destination_port_range     = security_rule.value.port
      source_address_prefix      = "*"
      destination_address_prefix = "*"
    }
  }

  lifecycle {
    prevent_destroy = true
  }
}
```

This is exactly the layering you'll see in real-world Terraform code:
validation guards the input, a conditional expression picks the right
name, a `for` loop over a `locals` map drives a dynamic block, and a
lifecycle rule protects the finished resource — each language feature
doing the one job it's actually suited for.

## 12. Common Pitfalls Across All of These

**Using splat on a `for_each`-created (map-based) resource.** Section
6 — convert with `values()` first, or use a `for` expression instead.

**Trying to use a `dynamic` block to conditionally set a plain
argument.** Section 7 — dynamic blocks only generate nested blocks;
use a conditional expression directly on the argument instead.

**Assuming `validation` can reference other variables on any
Terraform version.** Section 9 — this specific capability requires
1.9+.

**Assuming `precondition`/`postcondition` are available on any
Terraform version.** Section 10 — requires 1.2+.

**Combining `ignore_changes = all` with a specific attribute list.**
Section 8 — mutually exclusive; pick one form.

**Forgetting `create_before_destroy` may need to propagate to
dependent resources.** Section 8 — check for dependency-ordering
errors if you add it to a resource with downstream dependents.

**Deep-nesting conditional expressions instead of using `lookup()`.**
Section 4 — readability degrades fast past one level of nesting.

**Forgetting the `iterator` argument exists for nested dynamic
blocks.** Section 7 — without it, colliding default iterator names
between an outer and inner dynamic block will shadow each other.

## 13. Version Notes Worth Checking

Rather than presenting every rule above as timelessly universal, here
is a consolidated list of the version-dependent behaviors covered in
this guide — check `terraform version` against these if something
here doesn't work as described:

- `precondition` / `postcondition` blocks: require Terraform 1.2 or later
- `validation` conditions referencing a *different* variable (not just
  the variable being validated): require Terraform 1.9 or later
- Optional object-type attributes with defaults (`optional(string,
  "default")` inside an `object({})` type constraint) — a related,
  commonly-confused feature not covered in depth in this guide: require
  Terraform 1.3 or later

If you're working in a codebase pinned to an older provider or
Terraform core version (Day 2's version-constraint discussion), always
verify a given syntax is actually supported before assuming a "syntax
error" is a mistake in your own code rather than a version mismatch.

## 14. Quick Reference Summary

Conditional expression: `condition ? true_value : false_value` — picks
between two values.

`for` expression: `[for x in collection : expr]` (list) or `{for k, v
in collection : k => expr}` (map) — transforms a collection, with
optional `if` filtering.

Splat expression: `resource.name[*].attribute` — shorthand for a `for`
expression pulling one attribute from every item in a *list*; does not
work directly on maps or `for_each`-created resources without
`values()` first.

Dynamic block: `dynamic "block_label" { for_each = ...; content { ... } }`
— generates a variable number of repeatable *nested blocks*; the
optional `iterator` argument renames the loop variable, essential when
nesting dynamic blocks inside each other.

Lifecycle block: `create_before_destroy`, `prevent_destroy`,
`ignore_changes`, `replace_triggered_by`, `precondition`,
`postcondition` — controls how a resource is managed across its
lifecycle, distinct from its ordinary configuration arguments.

Variable validation: `validation { condition = ...; error_message =
... }` — checks an input variable before any plan/apply proceeds;
cross-variable references require Terraform 1.9+.
